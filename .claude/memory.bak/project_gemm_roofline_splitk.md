Full-batch dense layer (in=42, out=64, batch N=475355) on a 54-CU GPU, f64 peak ~1099 GFLOP/s. All three GEMMs are `hipblasDgemm` — we do NOT hand-tile, rocBLAS picks the kernel from the shape:
- forward `Y=X·W` (`gpu_gemm`, kernels.rs:1591): M=N_batch, N=64, **K=42**. Output huge → all CUs busy, but short K=42 → **bandwidth-bound → 511 GFLOP/s = 46.5% of peak** (NOT saturated).
- backward `dW=Xᵀ·grad` (`gpu_linear_backward_weights_only_into`, kernels.rs:3050): output **64×42** (tiny, ~2 tile-rows), contraction K=475355. rocBLAS tiles the tiny output → ~52/54 CUs idle, huge reduction serialized in a few workgroups → **45.6 GFLOP/s = 4.2%**. Parallelism/occupancy starvation, NOT tile selection. Bigger tiles can't help — no output to spread.
- backward `dX=grad·Wᵀ`: output huge (N×42) → fine, not the bottleneck.

Fix for dW: **split-K** over the 475355 axis (force a rocBLAS split-k solution via `rocblas_gemm_ex`, or custom split-K Dgemm with partial-sum reduction). Win is occupancy, not tile size.

**SHIPPED (this session):** custom two-pass split-K dW kernel — `splitk_dw_pass1`/`pass2` in `gpu-core/src/kernels/math.hip`, P-derivation `splitk_dw_p` in `math_ops.rs`, wrapper `gpu_splitk_dw_into` + `gpu_splitk_dw_partials_elems` in kernels.rs, `dw_partials` buffer in `Scratch` (allocate-once, sized to widest Dense + each Attn proj). Pass1 = one workgroup per (output-tile, K-slice) accumulating a [P×k×n] partial with 64×64 register-microtile + LDS staging; pass2 sums the P partials. **NO f64 atomicAdd** (two-pass = deterministic; validated vs rocBLAS `gpu_gemm_at` to ~1e-14 rel in `splitk_dw_matches_rocblas`). Wired into `gpu_linear_backward_full_into`, `gpu_linear_backward_weights_only_into` (each gained a `partials` param), and the out_dim==1 site (replaced `gpu_dgemv_into` in train.rs). Measured (Churn 42→64, N=475355): **56.3ms/4 workgroups → 7.25ms/432 workgroups (all 54 CUs, 8 waves) = 7.8×.** Caveats: ~538 GFLOP/s = 49% peak (k=42 masks 34% of BM=64; below the 90% stretch). The fixed 64×64 tile does full-tile work regardless of actual k,n → small-output layers cost the same 7.25ms; the out_dim==1 dW REGRESSED 4.8ms→7.25ms (the gemvt wasn't CU-starved). Net per-epoch dW still 60.8→14.5ms (4.2×). Opportunity: element-based register-accum kernel (no BM/BN padding) for small-n + a P sweep to the knee.

**Why:** I claimed forward was "~100% f64 peak" — wrong, it's 46.5%. The root error is asserting peak utilization without doing GFLOP/s-vs-peak arithmetic (same class as [[feedback_no_handwave_capability_audits]]). **How to apply:** before any "at peak" claim, compute measured GFLOP/s / hardware peak; for any tall-contraction/tiny-output GEMM, suspect CU starvation and reach for split-K, not retiling. Ties to [[project_no_minibatching]] (full-batch makes N huge, which is exactly what makes dW's output tiny relative to K).
