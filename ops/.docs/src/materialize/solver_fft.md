# Solver and FFT materialization

This document follows the two source-qualified operations owned by
`ops/src/materialize/solver_fft.rs`: `gpu_fft_c2c_1d` and `gpu_tri_solve`.
The module is not a vendor-library bridge. It turns prepared tensor tables and
verified facts into a finite `recipe-language::CalculationGraph` made only of
gathers, elementwise scalar programs, reductions, and unique scatters. The
graph is prepared before the run loop; placement, backend lowering, allocation,
synchronization, and lifecycle remain downstream responsibilities.

The source links below point at the exact implementation that defines the
behavior described here:

* [`solver_fft.rs`](../../../src/materialize/solver_fft.rs) owns exact family
  membership and the two symbol branches.
* [`materialize.rs`](../../../src/materialize.rs) owns request validation,
  repeat expansion, identity allocation, workspace accounting, graph emission,
  the two emitters, scalar programs, and shared checks.
* [`composition.rs`](../../../src/composition.rs) owns the descriptive recipes
  and their primitive-family order.
* [`registry.rs`](../../../src/registry.rs) derives source-qualified
  descriptors from the generated operation inventory.

## Ownership and dispatch

`solver_fft.rs` has one ownership table:

```rust
const OPERATIONS: &[(&str, &str)] = &[
    ("gpu_fft_c2c_1d", "gpu-core/src/linalg.rs:867"),
    ("gpu_tri_solve", "gpu-core/src/kernels.rs:2263"),
];
```

`supports` compares both tuple fields. A same-named descriptor from another
legacy source is not owned by this module. `dispatch` first calls `supports`;
when it is false it returns `FamilyDispatch::NotOwned`, allowing the central
dispatcher to try the next family. When it is true, the symbol selects exactly
one emitter and the result is wrapped in `FamilyDispatch::Owned`.

The central `dispatch_concrete` order is fixed. It probes
`optimizer_normalization`, then `solver_fft`, followed by attention/sequence,
convolution/pooling, loss/metrics, indexing/sort/encoding, graph/clustering/RL,
tree/boosting, inference/quantization/diffusion, creation/shape/misc, and
training. A `NotOwned` result is not an error. If no family owns a descriptor,
the central function returns `GraphMaterializationFailed` with a
source-qualified missing-dispatch message. The solver module's wildcard branch
also returns `GraphMaterializationFailed` if its ownership table and symbol
match ever drift.

`has_concrete_materializer` uses the same exact `supports` predicates before
dispatch. Therefore an unsupported source-qualified descriptor fails earlier
with `MissingConcreteFormula`; it cannot reach a neighboring emitter. In
particular, `gpu_rfft_1d` shares the `stockham_fft_1d` descriptive recipe in
`composition.rs`, but is absent from `OPERATIONS`, so it remains in the
remaining composition manifest and never gets the complex-to-complex emitter.

## Descriptor and recipe resolution

`OperationRegistry::describe` constructs an `OperationDescriptor` from a raw
surface row. `registry::lowering` checks scalar recipes, primitive recipes,
workspace formulas, non-calculation recipes, then composition recipes. Both
solver/FFT symbols select `LoweringAvailability::Composition`:

* `gpu_fft_c2c_1d` and `gpu_rfft_1d` map to `FFT_STEPS`, payload
  `CompositionPayload::F32AndI32`, and family `OperationFamily::Fft`.
* `gpu_tri_solve` maps to `TRIANGULAR_SOLVE_STEPS`, payload
  `CompositionPayload::F32`, and family `OperationFamily::Solver`.

For these exact arms the composition lookup is keyed by symbol. Concrete
ownership is still source-qualified in `solver_fft.rs`. The recipe's payload
becomes the descriptor's canonical dtype contract. The general registry rules
classify both symbols as `AliasContract::OperationSpecific` (they are `gpu_`
operations that do not end in `_into`) and
`DeterminismContract::FixedPrimitiveOrder` (they own compositions). Neither
has an excluded legacy dtype. The alias field is descriptor metadata; emitted
graph kernels independently receive a forbidden rule for every input/output
pair.

`CompositionRecipe::validate` requires nonempty name, definition, and top-level
steps; every role must be nonempty; repeat bodies must be nonempty; fixed
counts cannot be zero; prepared parameter names cannot be empty; nesting is
limited to eight levels. The FFT and triangular recipes satisfy those checks.

### Recipe step trees

The FFT recipe is one repeat:

```text
repeat CeilingLog2ShapeExtent(axis 0), role "execute every radix-2 Stockham stage"
  Gather       "read bit-reversed butterfly partners"
  Elementwise  "apply owned sine/cosine twiddles and complex pair arithmetic"
  Scatter      "write disjoint butterfly outputs"
```

The triangular recipe is one repeat:

```text
repeat ShapeExtent(axis 0), role "perform statically bounded forward or backward substitution"
  Reduce       "form the known-prefix dot product in fixed order"
  Elementwise  "check the diagonal and solve the next component"
  Scatter      "write the disjoint solved component"
```

The role strings are descriptive metadata. They do not execute an operation or
introduce a host loop. `expand_composition` resolves the bound from the shape
of the request's named iteration input, records a `ResolvedBound`, and recursively
unrolls the body. Each `ResolvedStep` stores its ordinal, family, role,
surrounding repeat indexes, and a dependency on the immediately previous
resolved step. Expansion has a fixed one-million-step limit.

## Shared materialization path

The public `recipe::operations::materialize` facade delegates directly to
`recipe_ops::materialize_composition`. Advanced callers can construct the same
request through `recipe::engine::ops`. The concrete path is:

1. A caller resolves a descriptor from the registry, supplies named boundary
   tensors, chooses the input whose shape supplies repeat bounds, fixes typed
   preparation facts, and reserves value and kernel identity ranges.
2. `materialize_composition` runs `validate_request`. The descriptor must own a
   composition; there must be at least one input and output; all names and tensor
   IDs must be unique; every tensor must validate; inputs must be external
   inputs; outputs must be non-input external outputs.
3. The central concrete-materializer predicate checks exact source-qualified
   ownership. Missing ownership returns `MissingConcreteFormula` before shape
   expansion or graph emission.
4. The named `iteration_shape_input` is looked up only among inputs. A missing
   name returns `InvalidMaterializationRequest`.
5. `expand_composition` validates the recipe, resolves the shape bound, and
   produces the finite `ResolvedComposition`.
6. `Emitter::new` creates a `GraphBuilder` at the caller's identity namespace.
   `dispatch_concrete` invokes the solver branch, which allocates intermediates
   and emits primitive kernels in the resolved order.
7. `Emitter::emit_stage` checks that a nonempty emitted sequence belongs to the
   next resolved step. The family of the last kernel in the sequence must equal
   the resolved step family. This is why a triangular reduce step may contain
   an elementwise multiply followed by a reduce: the last kernel is the reduce.
8. `Emitter::finish` requires that every resolved step was consumed, finalizes
   the graph and workspace allocation, and returns `MaterializedComposition`.

`MaterializedComposition` preserves the operation ID, validated graph, resolved
recipe, `StageEmission` map, `WorkspaceAllocation`, and the namespace used to
create all intermediate values and kernels. No callback, runtime recipe, or
data-dependent host iteration is stored in the result.

### Shared graph and identity invariants

`GraphBuilder::new` clones all declared input and output tensors, computes the
half-open value and kernel ranges, and rejects a declared tensor ID inside the
reserved intermediate-value range. `intermediate` allocates a contiguous
F32/I32 tensor with a fresh `ValueId`, computes its storage bytes, checks the
workspace limit, and records a `WorkspaceObject`. `emit` assigns the next
`KernelTemplateId`, creates forbidden alias rules for every input/output pair,
and appends a `CalculationNode`.

`CalculationGraph::validate` then checks tensor layouts, duplicate tensors and
kernels, unknown values, duplicate producers, external-boundary rules, every
primitive's dtype/shape/signature, and acyclicity. The graph's dependency order
is inferred from value producers. `ResolvedStep.dependencies` is retained as
preparation metadata and is not a second scheduling mechanism.

Every index primitive emitted here uses `IndexBounds::Reject`, so backend
lowering attaches a checked index-out-of-bounds fault channel. Every scatter
uses `ScatterConflict::UniqueIndices`, so no payload atomic policy is needed.
The lowerer still realizes a unique scatter as a copy of the base followed by
the indexed write. A graph scatter is therefore one calculation node but can
contain two backend stages.

Neither emitter calls the shared `require_exact_abi` helper. The actual code
requires the names it looks up and validates their dtypes/shapes, but it does
not reject extra parameter keys or extra input names at the family boundary.
An unused extra input is still an external tensor and can survive graph
validation. An extra output is never produced by these emitters, so final graph
validation reports a missing producer (wrapped as `GraphMaterializationFailed`).
The required facts and `tree_lanes` are checked explicitly; unknown parameters
are otherwise ignored.

## `gpu_fft_c2c_1d`: radix-2 complex FFT

### Boundary ABI

The emitter first looks up four boundary names:

| Role | Name | Required contract |
| --- | --- | --- |
| real input | `real` | external F32, rank one |
| imaginary input | `imaginary` | external F32, same dtype and shape as `real` |
| real output | `transformed_real` | external F32, same dtype and shape as `real` |
| imaginary output | `transformed_imaginary` | external F32, same dtype and shape as `real` |

The real input's rank must be exactly one. Its element count `N` must be at
least two and a power of two. `N` must be at most `MAX_I32_INDEX` (`2_147_483_647`)
so that checked index arithmetic remains in the int32 domain. The largest
accepted power-of-two extent is therefore `2^30`.

Two boolean prepared facts are mandatory and must be true:

* `fft_stage_tables_verified`
* `fft_destination_indices_unique`

For every resolved stage `s`, the request must contain these input tensors:

| Stage inputs | Dtype and shape |
| --- | --- |
| `stage_s_left_indices`, `stage_s_right_indices` | I32 `[N]` |
| `stage_s_real_from_left_real`, `stage_s_real_from_left_imaginary`, `stage_s_real_from_right_real`, `stage_s_real_from_right_imaginary` | F32 `[N]` |
| `stage_s_imaginary_from_left_real`, `stage_s_imaginary_from_left_imaginary`, `stage_s_imaginary_from_right_real`, `stage_s_imaginary_from_right_imaginary` | F32 `[N]` |
| `stage_s_real_base`, `stage_s_imaginary_base` | same dtype and shape as `real` |
| `stage_s_destination_indices` | I32 `[N]` |

`require_shape` checks the index and coefficient extents exactly. The base
vectors are checked by `require_same_tensor_contract`, which compares dtype and
shape. Layout and storage are validated later by the language graph contract,
but these helper checks do not require the boundary layouts to be identical.

### Static expansion

For `N = 2^k`, `ceiling_log_two(N)` resolves to `k`. Expansion therefore
creates one bound with value `k` and `3*k` resolved steps, in repeated
Gather/Elementwise/Scatter order. There is no runtime loop over stages. A
non-power-of-two extent is rejected by the emitter after expansion, so the
descriptive bound alone does not broaden the accepted shape domain.

### One emitted stage

The emitter carries `current_real` and `current_imaginary` value IDs. They
start at the two external inputs and become the prior stage's scatter outputs.
For each stage:

| Resolved step | Emitted graph kernels | Inputs and outputs | Primitive details |
| --- | --- | --- | --- |
| Gather | four kernels | `current_real` and `current_imaginary`, each read at left and right index vectors; four new F32 `[N]` intermediates | `Gather { axis: 0, bounds: Reject }` for every kernel |
| Elementwise | one kernel | four gathered vectors plus eight coefficient vectors in; `updated_real` and `updated_imaginary` F32 `[N]` out | two-output `Elementwise` using `fft_linear_stage_program` |
| Scatter | two kernels | real and imaginary stage bases, one destination vector, and one updated vector in; next real/imaginary image out | `Scatter { axis: 0, bounds: Reject, conflict: UniqueIndices }` |

The final scatter writes `transformed_real` and `transformed_imaginary`; every
earlier scatter writes fresh F32 `[N]` intermediates. The destination uniqueness
fact is the preparation proof for the `UniqueIndices` conflict policy. The
runtime `Reject` bounds still report malformed prepared index values through
the fault channel instead of performing unchecked memory access.

`fft_linear_stage_program` creates twelve F32 scalar inputs in the same order as
the graph inputs. It forms each output as a four-term weighted sum:

```text
real      = left_real      * c_real_from_left_real
          + left_imaginary * c_real_from_left_imaginary
          + right_real     * c_real_from_right_real
          + right_imaginary* c_real_from_right_imaginary

imaginary = left_real      * c_imaginary_from_left_real
          + left_imaginary * c_imaginary_from_left_imaginary
          + right_real     * c_imaginary_from_right_real
          + right_imaginary* c_imaginary_from_right_imaginary
```

The first term is a `Multiply`. Each subsequent term is added with an explicit
one-rounding `Fma(value, coefficient, accumulated)`. The scalar builder fixes
the typed SSA instruction order, and `ScalarProgram::validate` checks arity,
dtype, definition order, and outputs before the elementwise kernel is accepted.
The coefficients are prepared data. The emitter does not calculate sine or
cosine values and does not call an FFT library.

### FFT graph and resource accounting

For `k = log2(N)`:

| Resource | Exact count or formula |
| --- | --- |
| Resolved composition steps | `3*k` |
| `StageEmission` records | `3*k` |
| Graph kernels | `4` gathers + `1` elementwise + `2` scatters per stage = `7*k` |
| Intermediate values | `4` gather outputs + `2` butterfly outputs + `2` nonfinal scatter outputs per nonfinal stage, and no final scatter outputs = `8*k - 2` |
| Workspace bytes | every intermediate is F32 `[N]`, so `4*N*(8*k - 2)` bytes |
| Identity capacities required | at least `8*k - 2` value IDs and `7*k` kernel IDs |

The caller's namespace, not the emitter, defines the available capacities. The
in-tree training and inference generic materializers reserve 64 values and 64
kernels. Under that caller envelope, FFT values fit through `k = 8` (`N <= 256`);
`N = 512` needs 70 intermediate values and fails with
`IdentityNamespaceExhausted` even though 63 kernels would fit. A direct caller
may reserve a larger namespace. Any smaller workspace limit is enforced as
each intermediate is allocated; no estimate or fallback path is used.

### FFT failures and invariants

* Missing or duplicated names, duplicate IDs, invalid tensor layouts, wrong
  external flags, or a missing `real` iteration input return
  `InvalidMaterializationRequest` before emission.
* Wrong boundary dtypes, missing stage tensors, wrong index/coefficient shapes,
  a non-rank-one input, a length below two, a non-power-of-two length, or a
  length above `MAX_I32_INDEX` return `UnsupportedConcreteShape` or the
  corresponding request error from the helper that observed it.
* Missing or mistyped stage facts return `MissingPreparedParameter` or
  `PreparedParameterTypeMismatch`; a false fact returns
  `InvalidMaterializationRequest`.
* An unrepresentable stage-count conversion returns an operation-tagged request
  error. The recipe's fixed expansion limit can also return
  `CompositionExpansionOverflow`, although the explicit FFT int32 extent check
  is normally the tighter bound.
* Exhausted value/kernel ranges, checked workspace overflow, or a workspace
  limit failure return `IdentityNamespaceExhausted`,
  `WorkspaceArithmeticOverflow`, or `WorkspaceLimitExceeded`.
* A stage-family mismatch, too many or too few emitted stages, malformed scalar
  SSA, or final graph validation failure returns `GraphMaterializationFailed`.

## `gpu_tri_solve`: statically ordered triangular substitution

### Boundary ABI

The boundary consists of one base image and one output:

| Role | Name | Required contract |
| --- | --- | --- |
| initial solution image | `solution_base` | external F32, nonempty rank one |
| solved image | `solution` | external output, same dtype and shape as `solution_base` |

The code rejects rank zero, rank greater than one, and a rank-one shape with
zero elements. It requires three true preparation facts:

* `solution_base_zero`
* `triangular_rows_verified`
* `destination_indices_unique`

The `tree_lanes` prepared parameter is read as `U64`, converted to `u32`, and
must be a power of two in `1..=1024`. For each row `r` in `0..N`, where `N` is
the solution extent, four inputs are required:

| Row input | Dtype and shape | Role |
| --- | --- | --- |
| `row_r_strict_prefix` | F32 `[N]` | verified strict-prefix coefficient image |
| `row_r_rhs` | F32 `[1]` | right-hand-side scalar |
| `row_r_diagonal` | F32 `[1]` | diagonal pivot |
| `row_r_destination` | I32 `[1]` | checked destination index for the solved scalar |

The emitter does not inspect the numeric values represented by the three facts.
The caller's preparation phase is responsible for proving those properties;
the emitted graph still checks index bounds and diagonal nonzero-ness at runtime.
There is no direction parameter. The concrete loop visits row ordinals in
ascending order and lets the prepared strict-prefix and destination tables
encode the intended substitution layout. The recipe definition's “forward or
backward” wording is not a runtime branch.

### One emitted row

`current` starts at `solution_base` and is replaced by each row's scatter image.
For every row the emitter allocates and emits:

| Resolved step | Emitted graph kernels | Inputs and outputs | Primitive details |
| --- | --- | --- | --- |
| Reduce | two kernels in one `StageEmission` | `row_r_strict_prefix` and `current` produce `terms` F32 `[N]`, then `terms` produces `prefix` F32 `[1]` | first kernel is F32 elementwise multiply; second is `Reduce { operator: Sum, axes: [0], keep_dimensions: false, result: Value, tree_lanes }` |
| Elementwise | one kernel | `row_r_rhs`, `prefix`, and `row_r_diagonal` produce `solved` F32 `[1]` | `triangular_solve_program` checks the diagonal, subtracts the known prefix, and divides |
| Scatter | one kernel | `current`, `row_r_destination`, and `solved` produce `next` | `Scatter { axis: 0, bounds: Reject, conflict: UniqueIndices }` |

The first row's multiply is the product of a verified coefficient image and the
zero base image. Each later row sees the prior scattered solution image. The
final row writes the external `solution`; nonfinal rows write fresh F32 `[N]`
intermediates.

`triangular_solve_program` is a typed scalar SSA program with F32 inputs
`rhs`, `prefix`, and `diagonal`. It creates the F32 constant zero, evaluates
`diagonal != 0` as an I32 predicate, applies `Require` to publish an arithmetic
fault if the predicate is zero, computes `rhs - prefix`, and divides by the
diagonal:

```text
require(diagonal != 0)
solved = (rhs - prefix) / diagonal
```

`Require` is an explicit fault-producing scalar operation, not a host-side
conditional or a replacement diagonal. During backend lowering this program
therefore receives an arithmetic-domain fault flag. The reduction's
`tree_lanes` fixes the collective tree and its floating-point order. The
scatter's `Reject` mode separately supplies an index-out-of-bounds fault path.

### Triangular graph and resource accounting

For `N = solution_base.shape.elements()`:

| Resource | Exact count or formula |
| --- | --- |
| Resolved composition steps | `3*N` |
| `StageEmission` records | `3*N` |
| Graph kernels | `2` for the reduce stage + `1` solve + `1` scatter per row = `4*N` |
| Intermediate values | four per nonfinal row (`terms`, `prefix`, `solved`, `next`) and three for the final row = `4*N - 1` |
| Workspace bytes | `(2*N - 1)` F32 vectors plus `2*N` F32 scalars = `8*N^2 + 4*N` bytes |
| Identity capacities required | at least `4*N - 1` value IDs and `4*N` kernel IDs |

The 64-value/64-kernel reservation used by the generic training and inference
callers therefore admits `N <= 16` (`63` values and `64` kernels). At `N = 17`
the reserved kernel range is exhausted during the next row's reduce stage, and
the value demand would also exceed the range. Direct callers must reserve the
actual requirement or receive `IdentityNamespaceExhausted`. The materializer
has no dedicated int32 extent check for `N`; expansion, identity, workspace,
shape byte arithmetic, and downstream index validation remain the applicable
limits.

### Triangular failures and invariants

* The shared request checks and missing required names use the same
  `InvalidMaterializationRequest` boundary as FFT. Extra input names can remain
  unused; extra output names fail final graph validation because no producer
  writes them.
* A non-F32 base, a solution with a different dtype or shape, a rank-zero or
  empty solution, a missing row declaration, a row coefficient shape other than
  `[N]`, or a row scalar shape other than `[1]` returns a request or
  `UnsupportedConcreteShape` error.
* Missing, mistyped, or false facts return
  `MissingPreparedParameter`, `PreparedParameterTypeMismatch`, or
  `InvalidMaterializationRequest`. Missing or mistyped `tree_lanes` follows the
  same typed-parameter errors; zero, non-power-of-two, or greater-than-1024
  lanes return `InvalidMaterializationRequest`.
* `AxisSet::new([0])`, scalar builder construction, and scalar-program
  validation failures are wrapped as `GraphMaterializationFailed`. The
  constants are valid for every accepted nonempty rank-one shape, so these
  failures indicate a language-contract or implementation drift.
* A zero diagonal is not rejected during preparation by inspecting data. It
  trips the scalar `Require` fault when the graph runs. An out-of-range row
  destination likewise trips the scatter's checked index fault. There is no
  alternate pivot, clamping, or retry path.
* Expansion overflow, identity exhaustion, workspace arithmetic overflow, and
  workspace-limit failure retain their specific operation errors. Stage count,
  stage family, and final graph mismatches are `GraphMaterializationFailed`.

## Downstream end-to-end role

There is no in-tree call site that names `gpu_fft_c2c_1d` or `gpu_tri_solve`
directly. They are reachable through the generic structured-materialization
boundary. The production compiler callers have the same shape and state flow:

* `training/src/compile.rs` and `training/src/inference.rs` clone compiler
  tensors, mark temporary inputs/outputs as the fragment boundary, name them,
  resolve the symbol through `operation_registry().resolve_unique`, reserve a
  contiguous `MATERIALIZATION_RESERVATION` of 64 value IDs and 64 kernel IDs,
  and pass `WORKSPACE_LIMIT = u64::MAX` to `materialize_composition`.
* The training caller appends every returned tensor contract and node with the
  requested training or validation `IterationDomain`. The inference caller
  appends the same contracts and assigns `IterationDomain::first()`.
* Both callers normalize materialized tensors back to internal contracts when
  inserting the fragment. Their counters are advanced before the materializer
  call, so an error aborts compilation and never invokes a fallback or rolls
  back into a second implementation.
* At compiler finish, the assembled `CalculationGraph` is validated, serialized
  to canonical OGDL, decoded again, and wrapped in a
  `StaticCalculationProgram`. The program requires one explicit iteration
  domain for every kernel and checks dependency-domain initialization.
* `planner::plan_program_candidates` validates the program and graph, obtains a
  topological order, then calls `recipe_primitives::lower` for every emitted
  primitive kernel using measured lowering hardware. Gathers, reductions,
  scalar maps, and scatters become backend-neutral stages with checked buffers,
  fixed reduction trees, and fault/atomic contracts. Planner placement,
  scheduler dependencies, preparation allocations, native image loading, and
  the executor run those stages on the selected CUDA or HSA device. No stage in
  this path calls a vendor FFT or solver routine.

The operation's end-to-end role is therefore a pure preparation transformation:
prepared tables and facts become immutable f32/int32 graph values, graph nodes,
workspace accounting, and explicit fault behavior. The run loop consumes those
nodes according to the program's domains; it does not discover stages, create
twiddle coefficients, iterate rows on the host, or choose a diagonal policy.

## Failure vocabulary at the paired boundary

All failures are `OperationError` values carrying an `OperationErrorKind`, a
detail string, and the source operation's `OperationId` when the failure occurs
inside materialization.

| Boundary | Typical paired-operation cause | Result |
| --- | --- | --- |
| Registry | Missing symbol, ambiguous symbol-only lookup, or wrong source pair | `UnknownOperation` or `AmbiguousSymbol` before a request exists |
| Ownership | Descriptive composition has no exact family owner, such as `gpu_rfft_1d` | `MissingConcreteFormula` |
| Request | Empty/duplicate names or IDs, invalid tensor contract, wrong external flags, missing iteration-shape input | `InvalidMaterializationRequest` |
| ABI lookup | Required boundary, stage, or row name absent | `InvalidMaterializationRequest` |
| Dtype/shape | Non-F32 payload, wrong index/coefficient extent, invalid FFT length, empty triangular image | `InvalidMaterializationRequest` or `UnsupportedConcreteShape` |
| Prepared facts | Missing, mistyped, or false verification facts; invalid `tree_lanes` | `MissingPreparedParameter`, `PreparedParameterTypeMismatch`, or `InvalidMaterializationRequest` |
| Recipe expansion | Unresolved shape axis, invalid recipe, or more than one million resolved primitive steps | `IterationBoundUnresolved`, `InvalidCompositionRecipe`, or `CompositionExpansionOverflow` |
| Identity | Boundary ID in an intermediate range, overlapping caller ranges, or too few value/kernel IDs | `IdentityNamespaceOverlap` or `IdentityNamespaceExhausted` |
| Workspace | Checked byte addition overflows or the caller limit is exceeded | `WorkspaceArithmeticOverflow` or `WorkspaceLimitExceeded` |
| Emission | Wrong resolved family, empty stage, too many/few stages, or solver table/branch drift | `GraphMaterializationFailed` |
| Graph/language | Invalid scalar SSA, primitive signature, duplicate producer, missing producer, or cycle | `GraphMaterializationFailed` wrapping the language error |
| Runtime fault | Reject gather/scatter index or zero triangular diagonal | Device fault flag consumed by downstream execution; preparation does not substitute data |

No failure path retries with another family, calls a legacy implementation,
clamps an index, replaces a zero diagonal, or creates a vendor workspace. The
observed error remains at the boundary that owns the violated invariant.
